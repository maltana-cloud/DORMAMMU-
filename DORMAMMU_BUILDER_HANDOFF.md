## 1. What DORMAMMU Is

DORMAMMU is the permanent product/project identity: a **general-purpose autonomous intelligence and ecosystem platform**.

It is not merely:
- a chatbot;
- a news bot;
- a Telegram bot;
- a trading bot;
- a rental bot;
- a collection of unrelated AI agents;
- a marketing system; or
- a single model.

Its long-term direction is one coordinated system with many specialized capabilities that can understand the world, discover needs and opportunities, create useful solutions, distribute them, create legitimate awareness, realize sustainable value, measure outcomes, learn, and evolve within bounded authority.

Preferred brand motto:

**Beyond What Is Known.**

## 4. Protected Foundation

DORMAMMU is locked in **principles, authority boundaries, security, truth/provenance, owner control, identity/trust, audit, recovery protections, and architectural direction**.

It is deliberately **not frozen in future capability**.

Future capabilities must be additive, modular, versioned, tested, observable, reversible where practical, and compatible with existing contracts.

Core distinctions must remain intact:

`INTELLIGENCE ≠ AUTHORITY`

`CAPABILITY ≠ AUTHORITY`

`MODEL OUTPUT ≠ TRUTH`

`MEMORY ≠ CURRENT AUTHORITY`

`PROVIDER ≠ AUTHORITY`

`CREDENTIAL ≠ PERMISSION`

`IDENTITY ≠ AUTHENTICATION ≠ SESSION ≠ CAPABILITY ≠ AUTHORITY`

`OBSERVE → UNDERSTAND → PLAN → PERMISSION CHECK → SECURITY CHECK → ACT → VERIFY → RECORD → IMPROVE`

The unknown frontier remains open. A new builder should extend the architecture rather than prematurely pretending every future capability is already solved.

## 7. Universal Economic / Commercial Direction

DORMAMMU's economic architecture is not limited to forex, crypto, or currency.

It is intended to understand:

`NEEDS → PROBLEMS → BOTTLENECKS → INEFFICIENCIES → MARKET GAPS → OPPORTUNITIES → SOLUTIONS → VALUE → VALUE CAPTURE → MEASUREMENT → LEARNING`

Economic value is broader than money. Currency is a representation/measurement/settlement dimension, not the source of value.

The integrated architecture is:

`WORLD MODEL ↔ KNOWLEDGE FABRIC ↔ FINANCE MODEL ↔ OPPORTUNITY ENGINE ↔ ENTERPRISE MODEL ↔ AGENT/BOT FACTORY ↔ PRICING ↔ CURRENCY ↔ COMMERCE/PAYMENTS ↔ GROWTH/DISTRIBUTION ↔ AUTHORIZED ACTIONS ↔ MEASURED OUTCOMES ↔ LEARNING`

See `DORMAMMU_ECONOMIC_INTELLIGENCE_AND_WEALTH_ENGINE.md` for the canonical detailed contract. Do not create another parallel economic architecture document unless the owner explicitly changes the documentation structure.

## 8. Universal Agent / Bot Factory Direction

DORMAMMU should eventually be able to determine whether an identified problem calls for a bot/agent, workflow automation, software product, human-AI system, or another solution.

When an agent/bot is appropriate, the intended lifecycle is:

`DISCOVER → QUALIFY → SPECIFY → DESIGN → BUILD → TEST → SIMULATE/VALIDATE → REQUEST/VERIFY PERMISSION → DEPLOY IF AUTHORIZED → OBSERVE → OPTIMIZE → SCALE OR RETIRE`

The factory should be composable rather than a free-form code generator only. Shared building blocks can include data/perception, knowledge, reasoning, planning, memory/state, tools/providers, policy, execution, monitoring, evaluation, billing, monetization, growth, and recovery.

Potential outputs span **every domain** rather than a fixed list: finance, trading analysis, rentals/property operations, sales, commerce, logistics, education, research, agriculture, manufacturing, media, communities, software, services, operations, and domains not yet known.

The domain changes; the underlying DORMAMMU contracts and authority boundaries do not.

## 9. Pricing, Currency, Payments and Value

DORMAMMU should eventually be able to calculate an **exact proposed commercial amount** when sufficient evidence permits, rather than relying only on developer-hardcoded prices.

Pricing should consider value, demand, willingness-to-pay signals, market, competition, customer segment, delivery/operating cost, risk, complexity, acquisition cost, expected margin, long-term value, affordability, transparency, convenience and user welfare.

Currency intelligence should understand local and multi-currency contexts, including billing, accounting/reporting, settlement, exchange rates, timing/provenance, inflation/purchasing-power context and conversion costs where data is available.

Payment intelligence should select appropriate mechanisms based on customer comfort, jurisdiction, platform, currency, product, fees, reliability, security and applicable rules. Possible rails include cards, bank transfer, mobile/local methods, wallets, processors, invoices, recurring/usage billing, marketplace mechanisms, platform-native billing and **Telegram Stars for eligible Telegram products/flows**, among others.

Keep these separate:

`VALUE ≠ PRICE ≠ CURRENCY ≠ PAYMENT METHOD ≠ PAYMENT FEE ≠ SETTLEMENT ≠ REVENUE ≠ PROFIT`

The calculated amount is a proposed price/term, not permission to charge. Customers/owners must agree before charges or binding commitments. No payment-control, KYC/AML, licensing, authentication or platform-rule bypass is allowed.

- Telegram communities/groups;
- social accounts/pages;
- websites and blogs;
- newsletters;
- media projects;
- educational communities;
- marketplaces;
- events;
- brands;

The intended loop is:

`OBJECTIVE → AUDIENCE DISCOVERY → POSITIONING → CONTENT/OFFER → CHANNEL SELECTION → DISTRIBUTION → AWARENESS → ENGAGEMENT → ACTIVATION → CONVERSION → RETENTION → REFERRAL → MEASURE → LEARN → IMPROVE`

Growth must optimize genuine value and legitimate reach, not fake popularity. No spam, impersonation, fake followers/members/votes/reviews/engagement, deceptive activity, harassment, or platform-control circumvention.

Do not optimize solely for views, likes, followers or impressions. Measure outcomes appropriate to the actual objective.

## 11. The Economic Value Loop

DORMAMMU should eventually connect discovery, creation, commercialization and growth:

`OBSERVE → ACQUIRE EVIDENCE → NORMALIZE → PROVENANCE → MODEL → DETECT NEEDS/PROBLEMS/GAPS → GENERATE OPPORTUNITIES → QUALIFY → SCORE → DESIGN SOLUTION/BUSINESS/AGENT → MODEL UNIT ECONOMICS → VALIDATE → PRICE → SELECT CURRENCY → SELECT PAYMENT/SETTLEMENT → LAUNCH IF AUTHORIZED → DISTRIBUTE → CREATE AWARENESS → MEASURE → VERIFY → LEARN → UPDATE → IMPROVE → SCALE WHEN EVIDENCE SUPPORTS IT`

The purpose is **sustainable value creation**, not extracting the maximum money from users.

## 12. User Comfort and Commercial Ethics

User comfort is an explicit design constraint.

DORMAMMU should consider convenience, affordability, trust, security, transparency, payment friction, local norms, cancellation, fees, and customer preference when designing commercial experiences.

It should not manipulate users into spending, hide charges, make cancellation intentionally difficult, secretly alter terms, make unauthorized charges, exploit vulnerability, or use deceptive urgency.

The commercial principle is:

**Create enough genuine value that users willingly choose the exchange.**

## 13. Authority and External Action

The new economic, bot, commerce, payment, growth, account, channel, community, and distribution capabilities do **not** get their own permission system.

They must use the existing authority flow:

`DISCOVER NEED → DEFINE CAPABILITY → EVALUATE → REGISTER/IMPLEMENT → REQUEST AUTHORITY → LIVE PERMISSION CHECK → SECURITY CHECK → EXECUTE → VERIFY → RECORD`

Consequential actions such as spending, payment collection, financial execution, sensitive account access, public communication, publishing, contracts, external deployments, ownership changes, or other irreversible/high-risk operations require appropriate live authorization.

Historical memory or a prior permission does not authorize today's action.

## 14. Production Reality

The architecture describes future capability targets as well as existing capabilities. **Do not assume the presence of a document means the capability is implemented.**

For any requested capability, inspect:

- implementation;
- contracts/interfaces;
- tests;
- integration points;
- configuration;
- provider adapters;
- security and permission checks;

- failure/recovery behavior;
- recent commits;

Never claim production readiness from documentation or repository CI alone.

## 15. How to Continue DORMAMMU

When given an engineering objective:

1. Reconstruct actual state.
2. Identify the current milestone and highest-priority unfinished work.
3. Find the smallest correct architectural gap.
4. Define/confirm a stable contract.
5. Implement additively.
6. Test normal and failure paths.
7. Test security/permission boundaries.
8. Verify integration and backward compatibility.
9. Update status/documentation truthfully.
10. Commit clearly.
11. Verify CI when available.
12. Continue to the next safe task rather than stopping at the first successful file change.

Pause for the owner only when the constitution requires it: authorization/credentials, spending, ownership/recovery action, critical security judgment, major architectural ambiguity, unavoidable provider limits, or a high-risk irreversible external action.
